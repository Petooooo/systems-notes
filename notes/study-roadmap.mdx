## 전체 학습 노트 색인

개념·커널 코드·파일시스템·스토리지·논문·코딩테스트를 다루는 **전체 기술 노트 29편**은 [학습 노트 전체 목차](https://petooooo.github.io/notes/study-curriculum/)에 분야별로 정리했다. 이 문서는 목표 일정과 검증 계획을 다루고, 각 노트는 기술적 메커니즘과 참고자료를 담는다. 글을 공개한 것과 실험을 검증한 것은 별개다.

## 0. 이 로드맵의 목적

2027년 봄 KAIST AI시스템학과 석사과정에 진학해 Operating Systems Laboratory(OSLab)에서 공부할 예정이다. 이 계획은 **2026년 11월 현재부터 입학 전까지의 준비, 석사 첫 학기, 이후 연구 주제 탐색**을 연결한 개인 학습 로드맵이다.

학부에서 컴퓨터공학·전자공학을 함께 공부했고, TFLite Micro memory planner와 FPGA CNN 가속기 프로젝트를 수행했다. Linux 내부 구조와 시스템 프로그래밍을 공부했고, 이후 실제 Linux/K3s 기반 시스템을 운영하면서 **서비스를 복구하는 것과 그 원인을 kernel/filesystem/storage 계층까지 설명하는 것은 다르다**는 사실을 느꼈다.

따라서 이번에는 다양한 기술을 넓게 나열하기보다 **Linux kernel → VFS/file system → page cache/writeback → block layer/NVMe/Flash → 실험과 논문**을 주축으로 깊이를 만들려고 한다.

> **표기 원칙:** 이 문서는 앞으로의 계획이다. “읽기”, “구현”, “측정”은 완료 상태를 별도로 기록하며, 아직 수행하지 않은 실험을 실제 성과처럼 쓰지 않는다. 기존에 공부한 개념과 앞으로 새로 만들 실험은 구분한다.

### 우선순위

| 우선순위 | 영역 | 이유 |
|---|---|---|
| P0 | Linux OS 기본기: process, scheduling, VM, synchronization | 커널 소스와 성능 분석을 이해하기 위한 전제 |
| P0 | VFS / ext4 / page cache / block I/O | 연구 관심을 가장 분명하게 표현하는 주축 |
| P1 | C/C++ system programming, tracing, `perf`, eBPF | 구현과 실험을 실제로 수행하는 수단 |
| P1 | Flash/SSD/NVMe/ZNS, crash consistency | OSLab storage 연구의 하위 계층 |
| P1 | 알고리즘·자료구조 | 코딩테스트 준비와 코드 구현 기본기 |
| P2 | xv6/Pintos, kernel module, tiny patch | 구현·디버깅 감각을 높이는 프로젝트 |

## 1. 공부한 내용과 앞으로 검증할 내용

| 구분 | 현재까지의 근거 | 다음에 필요한 작업 |
|---|---|---|
| Linux system programming | 시스템 프로그래밍·학부 학습 | 작은 POSIX 코드를 재구현하고 실패 조건 테스트 |
| ftrace/KernelShark | Raspberry Pi에서 함수/스케줄링 이벤트 관찰 경험 | 새로운 kernel에서 같은 목적의 trace 재수집 |
| VFS/Flash filesystems | VFS 구조와 control flow 학습 | 실제 파일 I/O 소스 경로 추적, 성능 관측 |
| K3s / storage 운영 | 실제 온프레미스 인프라 운영·장애 대응 | 커널·파일시스템 계층의 원인 분석을 격리된 실험으로 재현 |
| OSLab 논문 | GAZE의 abstract/introduction 중심으로 검토 | 전체 본문·실험·비교 대상까지 깊이 읽기 |
| Pintos/xv6 | 학습 후보로 정리 | 첫 구현 환경 구축 및 테스트 통과 증거 |
| Kernel patch | 장기 목표 | 소스 수정·빌드·실험 로그가 쌓인 뒤 작은 수정부터 |

기존 학습에서 가장 아쉬웠던 것은 **개념을 안다고 생각하는 것과 실제 동작을 설명하거나 수정할 수 있는 것의 차이**다. 앞으로는 각 주제를 읽은 뒤 “정의, 코드 위치, 측정 방법, 남은 질문”을 짧게라도 기록하려고 한다.

## 2. 일주일 학습 운영 원칙

군 복무와 입학 준비를 병행하는 기간에는 무리한 시간표보다 **작고 반복 가능한 학습 단위**가 중요하다.

### 기본 루틴 예시

| 주기 | 학습 | 예상 분량 | 남길 것 |
|---|---|---|---|
| 주 2회 | OS/Kernel 개념과 소스 | 한 주제의 핵심 흐름 | 한국어 기술 노트 1개 |
| 주 1~2회 | C/C++ 또는 tracing 실습 | 30~90분짜리 작은 재현 | 실행 환경·명령·결과 |
| 주 2회 | 알고리즘·코딩테스트 | 문제 2~4개 또는 1패턴 집중 | 풀이·반례·복잡도 |
| 주 1회 | 연구실 논문 읽기 | 1편의 일부 또는 1편 | 1쪽 리뷰/질문 |
| 주말 | 정리·복습 | 진도보다 누락 확인 | 체크리스트 갱신 |

시간이 부족한 주에는 **커널 개념 1개 + 알고리즘 1문제 + 논문 2쪽**처럼 최소 단위만 유지해도 된다. 중요한 것은 계획표에 채워진 날짜가 아니라 **실제로 설명·재현할 수 있게 됐는가**다.

### 상태 표기

- **Not started:** 읽거나 구현하지 않음.
- **Reading:** 문서·소스 파악 중.
- **Reproducing:** 예제/실험을 실제로 실행 중.
- **Verified:** 환경·방법·결과를 기록했고 재현 가능함.
- **Needs review:** 이해가 불확실하거나 결과가 예상과 다름.

이 상태값은 GitHub issue, 프로젝트 보드나 노트의 간단한 표에서 관리하면 좋다.

## 3. Phase A — 2026년 11월: OS 기본기와 시스템 콜

목표는 대학원 면담에서 나왔던 기본 질문들을 **교재 문장을 암기하는 수준이 아니라 실제 시스템 흐름으로 설명할 수 있게 되는 것**이다.

### Week 1. 프로세스와 파일 디스크립터

- Process와 thread의 주소 공간/자원 공유 차이
- `fork`, `execve`, `waitpid`, exit state
- File descriptor, open file description, inode, shared file offset
- `open`/`read`/`write`/`close`의 반환값·오류
- Pipe와 `dup`를 이용한 FD 상속 실습

**완료 기준:** 프로세스 두 개가 FD를 공유할 때 파일 오프셋이 달라지는 조건을 말로 설명하고, 작은 코드를 실행해 확인한다.

### Week 2. Virtual memory

- `malloc`과 allocator, `brk`와 `mmap`
- VMA, page table, TLB, page fault
- Anonymous vs file-backed memory
- RSS/VIRT/PSS와 실제 물리 메모리
- Copy-on-write와 `fork`

**완료 기준:** page fault가 항상 오류가 아닌 이유, `mmap`을 했을 때 메모리가 언제 할당되는지 설명한다.

### Week 3. Synchronization과 CPU scheduling

- Runnable/Running/Sleeping, context switch
- Lock, mutex, semaphore, condition variable
- CFS와 vruntime의 역사적 모델
- Modern Linux의 EEVDF 관련 문서 검토
- Priority inversion, deadlock와 starvation

**완료 기준:** CPU 사용률이 낮은데 지연이 큰 상황에서 runnable delay와 blocked delay를 구분할 증거를 설명한다.

### Week 4. File API와 page cache

- VFS file, inode, dentry, superblock
- Buffered I/O, page cache, dirty page, writeback
- `fsync`/`fdatasync`, rename, directory sync 문제
- I/O가 커널을 거쳐 block layer로 내려가는 과정

**완료 기준:** `write()` 반환과 crash durability가 다른 이유를 구체적인 호출 흐름으로 설명한다.

## 4. Phase B — 2026년 12월: Linux 커널 구현과 관측

개념을 다시 읽은 뒤에는 **실제 이벤트 또는 소스 코드**와 연결해야 한다.

### Week 5. Kernel source 탐색

- 커널 소스 빌드·헤더·디버그 심볼의 관계
- `kernel/sched/`, `mm/`, `fs/`, `block/`의 역할
- `rg`/`cscope`/`ctags`/LSP 등을 이용한 심볼 찾기
- 호출 경로를 한 함수에 고정하지 않고 subsystem 단위로 추적

**산출물:** “하나의 시스템 콜이 어느 계층을 거치는가”라는 주제로 소스 경로·버전을 포함한 노트.

### Week 6. ftrace / trace-cmd / KernelShark

- `sched_switch` / `sched_wakeup` 이벤트
- Runnable 대기 시간과 CPU 실행 시간
- Trace 수집의 부하·파일 크기·시간 기준
- 이전에 관찰했던 스케줄러 타임라인을 새로운 실험으로 검증

**산출물:** 같은 workload를 두 번 실행해 trace 시각화 이미지와 해석을 남긴다. 과거 실험의 구체적인 측정값을 임의로 복원하지 않는다.

### Week 7. `perf`와 eBPF

- `perf stat`, CPU cycles, instructions, cache miss
- Sampling과 event tracing의 차이
- eBPF verifier, map, ring buffer의 역할
- BCC kprobe/kretprobe, 가능하면 tracepoint 우선 검토
- Kernel version과 BTF 지원 확인

**산출물:** 동일 작업에 대한 aggregate metric과 event trace가 어떤 질문에 답하는지 비교.

### Week 8. Block I/O와 `fio`

- Linux block layer, blk-mq, request queue
- NVMe submission/completion queue의 기초
- `fio` read/write, random/sequential, block size, queue depth
- Page cache, direct I/O, fsync/fdatasync 설정의 차이

**산출물:** 테스트 전용 파일과 볼륨을 사용한 실험 방법·결과·오해하기 쉬운 지표 목록.

## 5. Phase C — 2027년 1월: File System과 Flash/SSD 심화

이 단계의 목표는 OSLab의 파일시스템 논문을 읽을 때 **도입부의 문제 정의와 실험 절차를 실제 구현 계층과 연결하는 것**이다.

### Week 9. ext4와 Crash Consistency

- ext4 inode, extent, metadata, journal
- Journaling mode와 데이터 지속성
- `write` → dirty page → writeback → storage
- `fsync`, flush, write ordering, power-failure semantics
- Application transaction과 filesystem consistency 구분

**완료 기준:** 파일 변경 직후 장애가 나면 어떤 상태가 남을 수 있는지 논리적으로 설명한다.

### Week 10. F2FS와 Log-Structured Design

- Segment/section, log-structured allocation
- Data relocation, valid block, free space
- Garbage collection이 foreground I/O에 영향을 주는 이유
- Flash SSD FTL과 파일시스템 GC의 차이
- F2FS를 ext4와 같은 기준으로 비교하기 어려운 이유

**완료 기준:** F2FS에서 GC가 왜 필요한지, SSD 내부 GC와 무엇이 다른지 설명한다.

### Week 11. NVMe, ZNS와 Queueing

- NVMe의 submission/completion queue
- Queue depth, latency, throughput의 관계
- Zoned Namespace, sequential zone write 규칙
- Zone reset, open/active zone 제한
- ZNS SSD에서 host filesystem이 관리하는 책임

**완료 기준:** 기존 block SSD와 ZNS 장치에서 filesystem 설계가 달라지는 이유를 설명한다.

### Week 12. 첫 번째 Storage Mini-Lab

후보 실험:

1. **Page cache cold vs warm** 상태 비교.
2. **Buffered write와 sync write**의 응답 분포 비교.
3. Block I/O request latency에 영향을 주는 workload 파라미터 비교.
4. Test용 파일에서 `fio`로 sequential/random 패턴 비교.

**반드시 기록:** 커널, 파일시스템, mount option, SSD/가상디스크 환경, cache state, 데이터 크기, 큐 깊이, 실행 횟수, median/p95/p99, 관측 도구의 overhead.

디스크를 파괴하거나 운영 데이터를 변경하는 테스트는 하지 않는다.

## 6. Phase D — 2027년 2월: 논문 정독과 연구 질문 찾기

전역 후 연구실 참여·입학 준비와 병행할 단계다. 실제 일정은 연구실의 안내에 맞게 조정한다.

### 읽기 순서: 문제의식에 따라

| 우선 | 논문/연구 | 먼저 이해할 문제 |
|---|---|---|
| 1 | **GAZE** (SOSP 2026) | ZNS 환경 GC 중 CPU-side 상태/메모리 처리 병목과 pipeline |
| 2 | **D2FS** (FAST 2025) | 파일시스템 GC를 device-driven 방식으로 바꾸는 이유 |
| 3 | **OPIMQ** (FAST 2025) | Multi-queue block device에서 write ordering 보장 비용 |
| 4 | **f2trace** (ICPADS 2026) | NVMe queue-level tracing의 메모리와 오버헤드 |
| 5 | **DJFS** (FAST 2025) | 파일시스템 journaling의 granularity와 메타데이터 비용 |
| 6 | **GPUDirect Storage 성능 특성** (NVMSA 2026 poster) | GPU와 SSD 사이의 데이터 경로 및 병목 |
| 선택 | **CJFS / IPLFS / lwFSCK** | Journaling concurrency, GC 대안, recovery 비용 |

논문 제목·발표 정보는 [OSLab Publications](https://oslab.kaist.ac.kr/publications/)에서 확인했다. GAZE는 이전에 abstract/introduction 중심으로 검토했지만 **전체 설계·실험을 정독한 것으로 표시하지 않는다**.

### 한 편을 읽는 순서

1. 제목과 Abstract — 해결하려는 문제는 무엇인가?
2. Introduction — 왜 지금 중요하며 기존 방법의 한계는?
3. Background — OS·storage 지식이 부족한 지점은?
4. Motivation — 어떤 프로파일링 결과가 문제를 증명하는가?
5. Design — 어떤 구조를 바꿨는가?
6. Implementation — 실제로 어디에 구현했는가?
7. Evaluation — baseline과 workload가 공정한가?
8. Limitations — 적용하기 어려운 경우는?
9. My questions — 직접 검증하고 싶은 가설은?

### 논문 리뷰 템플릿

| 질문 | 작성 기준 |
|---|---|
| Research question | 한 문장으로 정의 |
| Motivation | 정량 근거가 있다면 표기 |
| Baseline | 기존 시스템·설정·비교 조건 |
| Mechanism | 핵심 변경점을 그림이나 경로로 설명 |
| Evidence | 수치가 어느 workload·장치에서 나왔는지 |
| Limitations | 장치 종속성, 재현 제약, 추가 비용 |
| Next experiment | 스스로 검증할 수 있는 작은 실험 |

가능하다면 **주 1편**을 읽되, 한 편을 정확히 이해하지 못했다면 두 번째 논문으로 넘어가기보다 실험/배경 지식을 보완한다.

## 7. Phase E — 2027년 봄학기: 연구실 입문과 Coursework

연구실에 참여한 뒤에는 아래 계획을 실제 과제·연구 지도에 맞게 조정한다.

### 1~4주: 환경과 재현성

- 연구용 Linux 환경, 소스 버전, 빌드 도구 파악
- 분석/실험용 데이터와 공개 가능 범위 구분
- 기본 baseline 실행 및 로그 기록
- 공동 작업 방식과 코드 리뷰 흐름 익히기
- 논문·실험 관리 노트의 형식 정리

### 5~8주: 후보 문제 검토

- Kernel/VFS/block I/O 중 직접 설명 가능한 경로 선택
- 논문에서 제시된 병목이 실제 환경에서도 나타나는지 확인
- 작은 실험을 통해 가설 1개를 반박 또는 지지
- 최소 재현 코드 또는 측정 스크립트 정리
- 성능과 정확성/일관성 측면의 trade-off 기록

### 9~16주: 작은 연구 과제로 압축

- 문제 정의와 baseline
- 병목에 대한 가설
- 대안 mechanism 1~2개
- 구현 난도와 예상 위험
- 측정 계획, 결과 해석, negative result 기록
- 지도교수·연구실 피드백을 반영해 범위 축소

목표는 초반부터 큰 논문을 쓰는 것이 아니라 **문제 → 메커니즘 → 검증**의 과정을 하나 끝까지 반복해 보는 것이다.

## 8. 이후 확장 트랙

연구 주제는 입학 후 정해질 수 있으므로 현재는 세 후보만 유지한다.

### Track A — Linux File Systems / Storage (우선)

VFS, ext4/XFS/F2FS, journaling, page cache, blk-mq, NVMe, ZNS/SSD. 가장 직접적인 관심과 연구실 연구축에 맞는다.

### Track B — Memory & Hardware-Aware Systems

Page reclaim, `mmap`, NUMA, tiered memory, CXL, GPU memory/I/O와 하드웨어 자원 관리. TFLite Micro memory planning 경험과 연결할 수 있다.

### Track C — Distributed/AI Infrastructure

Kubernetes, persistent volumes, distributed storage reliability, GPU serving, data pipeline. 이미 수행한 운영 경험을 연구 질문으로 발전시킬 때 선택한다.

현재 방향은 **A를 주축으로, B/C는 연구 필요에 따라 연결**하는 것이다. 세 트랙을 동시에 깊게 공부하겠다는 뜻은 아니다.

## 10. xv6·Pintos·Linux Kernel 실습 순서

### Step 1. OS 교육용 환경

xv6 또는 Pintos 중 하나만 먼저 선택한다. 둘 다 동시에 시작하지 않는다.

- 빌드·부팅·테스트 환경 준비
- Process/thread와 system call 구조 읽기
- Scheduler 또는 VM 관련 작은 기능 구현
- 테스트 케이스를 통해 동작 확인
- 변경 전후 결과와 코드 차이 기록

### Step 2. Linux 소스와 tracing

- 커널 버전 고정
- 관심 subsystem의 함수 호출 흐름 읽기
- ftrace, perf 또는 eBPF로 가설 확인
- 재현 가능한 workload와 결과 저장

### Step 3. Small patch

처음부터 새 파일시스템을 만들기보다 **작은 버그 수정, 문서 개선, 측정 도구, 로그 관측 개선**부터 검토한다. Upstream 제출은 코드 품질과 프로젝트 유지보수 정책을 이해한 뒤에 진행한다.

## 11. 실험의 품질 기준

커널·파일시스템 실험에서 **수치만 좋으면 성공**이라는 사고를 피하려고 한다.

### 실험 기록의 필수 정보

- Hardware: CPU, RAM, storage device / 가상 장치 여부
- Software: distro, kernel version, filesystem, mount options
- Workload: 파일 크기, block size, read/write 비율, queue depth, thread 수
- Metric: throughput, mean latency, p50/p95/p99, CPU, memory
- Baseline: 비교 대상의 동일 조건
- Repeat: 반복 횟수, 변동폭, warmup 여부
- Correctness: 데이터 일관성·정확성·복구 조건
- Limitations: 결과의 일반화 가능 범위

### Negative result를 남기기

실험이 실패했거나 기대한 성능 개선이 나오지 않아도 **재현 환경, 기존 가설, 왜 가설을 수정했는지**는 중요한 기록이다. 성과를 멋있게 보이게 만들기 위해 실패 사례를 지우지 않는다.

## 14. 공부가 막혔을 때의 판단 기준

| 막히는 상황 | 대응 |
|---|---|
| 커널 소스를 읽어도 함수 관계가 보이지 않음 | system call/API에서 출발해 호출 경로 범위 좁히기 |
| 논문이 너무 어려움 | 배경 subsystem을 1~2개만 먼저 복습 |
| 실험 결과가 일정하지 않음 | 환경·캐시·warmup·동시 부하 통제 |
| 시간이 부족함 | P0 주제 한 개만 이어가기 |
| 알고리즘 풀이가 반복해서 막힘 | 유형을 줄이고 반례·복잡도 복습 |
| 실습이 실패함 | 실패 상태·로그·가설을 그대로 기록 |
| 연구 방향이 흔들림 | 구현 가능한 실험 1개로 문제 범위 좁히기 |

## 15. 내가 앞으로 답하고 싶은 질문

- VFS에서 실제 block I/O까지 어떤 소프트웨어 오버헤드가 있는가?
- 파일시스템의 write ordering과 SSD의 내부 동작은 어떻게 상호작용하는가?
- Flash GC와 memory allocation이 tail latency에 얼마나 영향을 주는가?
- NVMe 다중 큐에서 요청 순서와 성능은 어떤 trade-off를 갖는가?
- eBPF/ftrace로 찾은 병목을 코드 수준에서 어떻게 개선할 수 있는가?
- GPU workload가 저장장치 데이터를 사용할 때 병목은 어느 계층에 있는가?
- 상위의 storage recovery 문제를 파일시스템/블록 계층의 증거로 얼마나 설명할 수 있는가?

위 질문을 지금 모두 해결할 필요는 없다. **하나를 작게 구현하고, 측정하고, 설명하는 능력**을 만드는 것이 가장 중요한 목표다.
