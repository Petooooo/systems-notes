## 어디서부터 볼까

Linux에서 프로그램 하나가 동작할 때도 여러 계층이 동시에 움직인다. 프로세스가 실행되고, 메모리 주소가 변환되고, 파일 경로는 VFS를 거쳐 해석된다. 데이터가 실제 저장장치에 도달하기까지는 page cache와 writeback, block layer가 한 번 더 관여한다.

K3s 기반 시스템을 운영하면서 장애를 복구하는 것과 **왜 그런 현상이 발생했는지 아래 계층까지 설명하는 것**이 다르다는 걸 자주 느꼈다. 그래서 관심이 가는 주제를 다음 흐름으로 묶었다.

[주제별 노트 모아보기](https://petooooo.github.io/notes/study-curriculum/)에서는 각 글을 바로 찾아볼 수 있다. 이 글은 **개별 기술이 어디에서 만나고, 어떤 순서로 읽으면 이해하기 쉬운지**에 초점을 둔다.

## 프로세스가 실행될 때

첫 번째 질문은 단순하다. **프로그램을 실행했을 때 커널은 무엇을 만들고 관리할까?**

- 실행 파일과 프로세스는 다른 대상이다. `execve()`는 실행 이미지를 교체하고, `fork()`는 자식 프로세스를 만든다.
- 프로세스마다 FD 번호는 따로 있지만, `fork()`나 `dup()`으로 열린 파일 상태를 공유할 수 있다.
- 같은 주소 공간의 thread는 메모리를 공유하므로 lock과 memory ordering을 함께 고민해야 한다.
- 스레드가 CPU에서 실행되지 않는 이유를 runnable 대기와 I/O·lock 등에 의한 sleep으로 나눈다.

관련 글:

- [프로세스·스레드·파일 디스크립터](https://petooooo.github.io/notes/study-process-fd-lifecycle/)
- [POSIX 시스템 프로그래밍](https://petooooo.github.io/notes/study-kdt-posix/)
- [Mutex·Semaphore·Memory Ordering](https://petooooo.github.io/notes/study-concurrency-locking-memory-order/)
- [CFS에서 EEVDF까지](https://petooooo.github.io/notes/study-scheduler-cfs-eevdf/)

확인하고 싶은 건 함수 이름을 얼마나 외우는지가 아니다. **`fork()` 뒤 파일 오프셋이 공유되는 이유**, **Runnable이 곧 Running이 아닌 이유**를 객체와 상태 변화로 설명할 수 있어야 한다.

## 주소 공간과 실제 메모리

`malloc()`의 반환값을 곧 물리 RAM이라고 보면 `mmap`, page fault, COW를 이해하기 어렵다.

| 눈에 보이는 것 | 내부에서 따져볼 것 |
| --- | --- |
| 프로세스의 VIRT | 주소 공간에 예약·매핑된 영역 |
| RSS와 PSS | 실제 상주하는 페이지와 공유 비중 |
| `mmap()` 성공 | 접근할 때 필요한 페이지가 모두 준비됐는가 |
| Page fault | 잘못된 접근인가, demand paging인가 |
| 컨테이너 OOM | Host pressure인가, cgroup limit인가 |
| 느린 메모리 접근 | NUMA locality와 reclaim 영향은 무엇인가 |

여기서 메모리라는 주제는 파일시스템과 다시 연결된다. File-backed mapping과 page cache는 별개인 듯 보이지만 둘 다 파일 데이터가 RAM에 머무르는 방식을 설명한다.

- [가상 메모리·mmap·Page Fault·COW](https://petooooo.github.io/notes/study-virtual-memory-mmap-fault/)
- [NUMA·Page Reclaim·Cgroup Memory](https://petooooo.github.io/notes/study-numa-reclaim-cgroups/)

## 커널 안에서 실제로 확인하기

개념을 이해했다고 생각해도 코드를 읽으면 막히는 경우가 많다. 커널 소스를 읽을 때는 **버전과 실행 조건부터 고정**하고, 사용자 API에서 출발해 해당 subsystem으로 내려가는 편이 낫다.

1. `read()`, `mmap()`, `sched_switch`처럼 출발점을 하나 정한다.
2. 관련 커널 tag와 config를 기록한다.
3. 상태를 관리하는 자료구조와 실제 호출 경로를 찾는다.
4. tracepoint 또는 작은 테스트로 예상한 동작이 보이는지 살핀다.
5. 설명되지 않는 분기는 그대로 남긴다.

자주 쓰게 될 도구의 역할도 다르다.

| 도구 | 주로 답하는 질문 |
| --- | --- |
| `ftrace` / `trace-cmd` | 어떤 커널 이벤트가 언제 발생했는가 |
| `perf` | CPU 시간과 하드웨어 이벤트가 어디에 쓰였는가 |
| eBPF/BCC | 특정 kernel event를 어떻게 골라 수집할까 |
| `crash` / vmcore | 시스템이 멈췄을 때 남은 상태는 무엇인가 |
| QEMU·xv6·Pintos | 격리된 환경에서 OS의 기본 구조를 수정할 수 있는가 |

이전에 Raspberry Pi에서 ftrace와 KernelShark로 실행 경로를 관찰한 경험이 있다. 다음에는 이벤트를 시각화하는 것에서 끝내지 않고, **어떤 지연을 측정했으며 다른 원인은 어떻게 제외했는지** 기록하려 한다.

## 파일을 열고 데이터를 쓸 때

가장 오래 붙잡고 싶은 부분이다.

파일 경로는 `dentry`와 `inode`를 거쳐 해석되고, 열린 파일의 상태는 `struct file` 같은 커널 객체로 표현된다. Buffered I/O는 page cache에서 처리될 수 있으며, dirty data가 실제 장치에 기록되기까지는 시간이 걸릴 수 있다.

그래서 다음 질문들이 자연스럽게 이어진다.

- `write()`가 성공했는데 전원 장애 뒤 데이터가 사라질 수 있는가?
- `fsync()`가 보장하는 범위는 정확히 어디까지인가?
- `rename()`의 원자성과 디렉터리 엔트리의 지속성은 같은가?
- 같은 파일을 두 번 열었을 때 두 FD는 무엇을 공유하는가?
- 파일을 삭제했는데도 저장 공간이 회수되지 않을 수 있는 이유는?

| 경계 | 중요한 객체·개념 |
| --- | --- |
| Application ↔ VFS | FD, file, dentry, inode |
| VFS ↔ Page cache | Address space, folio |
| Page cache ↔ Filesystem | Dirty data, writeback, journal |
| Filesystem ↔ Block layer | bio, request, blk-mq |
| Block layer ↔ Device | Queue, completion, flush |

- [VFS와 Path Lookup](https://petooooo.github.io/notes/study-vfs-pathwalk-inode-file/)
- [Page Cache·Writeback·fsync](https://petooooo.github.io/notes/study-page-cache-writeback-fsync/)
- [bio·blk-mq·NVMe Queue](https://petooooo.github.io/notes/study-block-io-blk-mq-nvme/)
- [ext4·JBD2·Crash Consistency](https://petooooo.github.io/notes/study-ext4-jbd2-crash-consistency/)

## SSD 아래에서 일어나는 일

NAND Flash는 데이터를 덮어쓰는 방식과 erase 단위에 제약이 있다. 그래서 FTL의 mapping, out-of-place update, GC, wear leveling이 필요하다.

그 위의 파일시스템도 공간을 관리한다. F2FS의 segment cleaning과 SSD 내부 GC는 서로 다른 계층의 작업이다. 어느 쪽이 얼마만큼의 비용을 만드는지 구별하는 데 관심이 간다.

ZNS는 여기서 한 단계 더 나아가 **Zone의 쓰기 위치와 공간 회수 책임 일부를 호스트에 노출**한다.

- [F2FS·Segment Cleaning·GC](https://petooooo.github.io/notes/study-f2fs-log-gc-segments/)
- [NAND Flash·FTL·Write Amplification](https://petooooo.github.io/notes/study-nand-ftl-write-amplification/)
- [NVMe·ZNS·Zone Lifecycle](https://petooooo.github.io/notes/study-nvme-zns-zone-lifecycle/)

이 부분을 읽을 때는 **CPU가 상태를 관리하는 비용**과 **장치가 실제 데이터를 이동하는 비용**을 따로 살핀다. 둘을 묶어 단순히 “SSD가 느리다”고 표현하면 어느 계층을 고쳐야 할지 알 수 없다.

## 측정하기 전에 정할 것

성능을 비교한다면 명령부터 실행하기보다 무엇을 검증하려는지 먼저 정해야 한다.

| 질문 | 통제할 조건 |
| --- | --- |
| 첫 읽기와 반복 읽기의 차이 | Cache 상태, 파일 크기 |
| Buffered와 Direct I/O | Filesystem, 정렬, I/O 크기 |
| `fsync` 비용 | 호출 간격, journal 설정 |
| Queue depth 증가 효과 | I/O engine, workload, 장치 |
| F2FS GC와 지연 | Free space, valid block 비율 |
| SSD의 성능 변동 | 온도, 내부 cache, GC 상태 |

실험 기록에는 kernel, filesystem, mount option, 테스트 장치, workload, 측정 횟수, p50/p95/p99, 실제 출력 파일과 한계를 남긴다. **값이 없으면 빈칸으로 둔다.** 예상한 효과와 실제로 관찰한 결과를 섞지 않는 것이 중요하다.

- [fio Workload 설계](https://petooooo.github.io/notes/study-fio-workload-design/)
- [Storage Mini-Lab](https://petooooo.github.io/notes/study-storage-mini-lab-method/)

## 구현과 알고리즘

커널과 파일시스템 코드만 읽어서는 구현 감각이 생기지 않는다. 작은 C/POSIX 코드로 API의 경계 조건을 확인하고, xv6/Pintos에서는 변경된 코드와 테스트 결과를 함께 남기는 편이 좋다.

알고리즘도 별도로 이어간다. 문제를 풀고 나면 **어떤 자료구조를 선택했고, 그 선택이 왜 맞는지**를 정리한다.

- [복잡도·배열·해시·스택·큐](https://petooooo.github.io/notes/study-algorithms-complexity-structures/)
- [Two Pointers·Binary Search](https://petooooo.github.io/notes/study-two-pointers-binary-search/)
- [BFS·DFS·Dijkstra·Union-Find](https://petooooo.github.io/notes/study-graph-bfs-dijkstra/)
- [DP·Greedy·Tree](https://petooooo.github.io/notes/study-dp-greedy-trees/)

개념과 풀이 과정은 `notes/`, 실제 소스와 실행 결과는 `labs/`에 둔다. 코드를 실행했다면 사용한 버전과 입력, 관찰된 출력을 연결한다.

## 계속 남겨둘 질문

- VFS에서 실제 block I/O까지 어떤 소프트웨어 비용이 발생할까?
- Dirty page의 writeback과 SSD 내부 GC는 tail latency에 어떻게 겹칠까?
- Multi-queue에서 높은 throughput과 write ordering을 함께 얻기 위해 어떤 비용을 지불할까?
- GC 도중 반복되는 memory allocation은 얼마나 비싼가?
- ftrace나 eBPF에서 본 지연을 커널 소스의 구체적인 경로와 연결할 수 있을까?
- GPU가 데이터를 기다릴 때 병목은 page cache, storage, transfer 중 어디에 있을까?

이 질문들에 한꺼번에 답하려는 것은 아니다. 하나씩 좁혀 보고, 직접 확인한 내용이 생길 때마다 관련 노트에 덧붙인다.
